# `ios-keyboard-missing` investigation

## Finding and change

No definite source-level cause of the missing Settings entry was found. The reported archive contains `Keyboard.appex`; its simulator Info.plist declares the keyboard extension point and `Keyboard.KeyboardViewController`; and `pluginkit` registers it in the iOS 26.5 simulator. The container app's own Settings page showing only Siri, Search, and Mobile Data is expected without a `Settings.bundle` and does not diagnose keyboard registration.

I made one safe build setting explicit in `ios/project.yml`: `APPLICATION_EXTENSION_API_ONLY: YES` for the extension. This makes extension-safe API checking unambiguous. It is **not** a demonstrated fix for discoverability. I did not rename the extension or change `PrimaryLanguage`: `mn` is a valid BCP 47 language tag, the original iOS task explicitly specified it, and neither change has evidence as a cause. The `Keyboard` product/module name matches the reported principal class, and the executable name alone should not hide a registered extension.

## Ranked hypotheses and CI diagnostics

The first useful CI addition is a UI test on the existing iOS 26 simulator: launch `com.apple.Preferences`, navigate **General → Keyboard → Keyboards → Add New Keyboard**, assert that the `TrustChain Keyboard` cell exists, and attach a screenshot of that page. `pluginkit` listing a plugin is necessary evidence, but does not show that Settings offers it. `defaults read` of keyboard preferences reports selected keyboards, not the available third-party list, so it cannot replace this UI check. Run the UI check after installing the Debug app and again with a Release simulator build. Then use these checks to narrow the cause:

| Rank | Hypothesis | Concrete CI simulator diagnostic and result to look for |
| --- | --- | --- |
| 1 | The installed TestFlight extension is not registered on the **device**, despite being present in the inspected archive. An export/re-signing difference or stale installation database could explain the gap. | CI should compare Debug and Release simulator installs: `test -f "$APP/PlugIns/Keyboard.appex/Keyboard"`, `plutil -p "$APP/PlugIns/Keyboard.appex/Info.plist"`, `xcrun simctl spawn "$DEV" pluginkit -mAvvv -i mn.trustchain.keyboard.ext`, then the Settings UI assertion. If both simulator variants are offered, inspect the **exported IPA** and on-device plugin/installation logs; simulator success cannot refute a TestFlight/device-only problem. |
| 2 | A device policy or Settings cache suppresses third-party keyboards. This fits an extension that registers elsewhere but never appears on this phone. | The Settings UI assertion on a clean simulator establishes whether the same OS family offers it. If it does, repeat on another unmanaged iPhone with the same build and check the affected phone's management/Screen Time restrictions and installation logs. CI cannot confirm or refute a particular phone's restrictions. |
| 3 | iOS 26.6.1 has a keyboard discovery rule or regression absent from 26.5. | Run the same Settings UI assertion on the latest available iOS 26 simulator runtime. Also install a minimal Xcode 26 keyboard-extension template into that runtime: if the template is listed and ours is not, inspect project metadata; if both are missing, investigate OS/runtime behavior. A 26.5 simulator result alone cannot settle a 26.6.1 device issue. |
| 4 | One Info.plist value is accepted by `pluginkit` but filtered by Settings: `PrimaryLanguage: mn`, identical app/extension display names, or a generated bundle key. | Capture `plutil -p` for both installed bundles and the Settings UI result. In isolated CI variants, change only `mn` to `mn-MN`, then only the extension display name to `Монгол гар`, regenerating and reinstalling each time. A variant appearing in Settings would implicate that value. Verify `CFBundleExecutable` names the bundled binary and `CFBundlePackageType` is `XPC!`. The existing extension point, principal class, and required keyboard attributes are present in the reported plist. |
| 5 | The extension binary cannot load, or its Swift principal class cannot be resolved. | After the Settings UI test, enable the keyboard and activate it in the container app's test field; capture `xcrun simctl spawn "$DEV" log show --last 5m --style compact --predicate 'eventMessage CONTAINS[c] "mn.trustchain.keyboard.ext"'`. Class/load errors or a crash would support this. If it is listed and types, this is refuted for the simulator. `PRODUCT_NAME: Keyboard` and `$(PRODUCT_MODULE_NAME).KeyboardViewController` are internally consistent. |
| 6 | Build settings or embedding differ between Debug and Release: extension-only API setting, deployment target, device family, or `Embed App Extensions` phase. | For both configurations, use `xcodebuild -showBuildSettings` for the `Keyboard` target and inspect the built app/appex: check `APPLICATION_EXTENSION_API_ONLY=YES`, `MinimumOSVersion <=` the simulator version, `UIDeviceFamily` contains `1`, and `PlugIns/Keyboard.appex` exists. The reported archive already embeds the extension; reported simulator metadata says iOS 15.0 and family `[1,2]`, which includes iPhone. An iPad value in addition to iPhone is harmless. |
| 7 | A sandbox profile or entitlement is missing. | Compare a working template keyboard's simulator install and `pluginkit`/system logs with ours, looking for a specific sandbox denial. iOS keyboard extensions use the system's app-extension sandbox; there is no project-specific sandbox profile requirement identified here. `RequestsOpenAccess: false` is intentional and should remain false. |

## Checks run and limits

- Parsed `ios/project.yml` with PyYAML and asserted the extension-only setting, app dependency, extension point, principal class, `PrimaryLanguage`, and `RequestsOpenAccess`. Passed.
- `git diff --check` passed.
- XcodeGen, Xcode, Swift/iOS compilation, simulator Settings UI, TestFlight export, and on-device checks were not run: this workspace is Linux and has no Xcode tools or iPhone.
